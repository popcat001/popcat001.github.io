How Anthropic Enables Self-Service Data Analytics with Claude

Source: claude.com/blog
Authors: Chen Chang, Clement Peng, Justin Leder, Johanne Jiao, Josh Cherry (Data Science & Data Engineering)
Date: June 3, 2026 · Estimated read time: ~18 min

🎯 Key Takeaways

  • The hard problem is ambiguity resolution, not SQL generation. An analytics agent fails because it can't reliably map a vague question to the specific, up-to-date data entity that answers it — not because it can't write a query.
  • Anthropic automates 95% of its business-analytics queries through Claude at ~95% aggregate accuracy. Adding structured "Skills" took accuracy from a 21% baseline to consistently above 95%, and ~99% in some domains.
  • Structure beats raw access. Giving Claude grep access to thousands of SQL files changed accuracy by less than one point. The bottleneck is structural mapping, not information availability.
  • "Data is not software." Code either compiles or fails; an analytics answer can look perfect and be silently wrong. There are no built-in guardrails, so correctness must be engineered through governance and validation.
  • A four-layer stack does the work: Data Foundations → Sources of Truth → Skills → Validation. Each layer targets one of three failure modes.
  • Generate docs with Claude, but let a human own the definition. Metrics live in a semantic layer so every surface in the company returns the same number.
  • Start small: a few canonical datasets, a few dozen offline evals, and one thin knowledge skill capture most of the upside before you build the rest.
  • Treat skill maintenance as a first-class citizen. Colocate skill markdown files in the same repo as the transformation models, so the PR that changes a model is the same PR that updates the doc describing it — this is how the docs stay in sync instead of silently going stale.
  • Treat query history as raw material for curation, not a source the agent reads directly. Historical SQL from dashboards and notebooks looks like the highest-value asset, but raw retrieval over thousands of prior queries moved accuracy <1 point — unstructured retrieval can't map a new question to the right precedent. Distill it into structured per-domain reference docs and reusable patterns instead.

Overview

This piece explains how Anthropic's data team built a system that lets non-experts ask business questions in plain language and get trustworthy answers from Claude — without a data scientist in the loop. The central insight is that reliable LLM analytics is an ambiguity problem: the model must connect a fuzzy human question to the one correct, current entity in a sprawling data model. The team solves this with a four-layer architecture and a heavy emphasis on validation. After reading, you'll understand each layer, why each exists, the experiments that proved what mattered (and what didn't), and how to start building a smaller version yourself.

Prerequisites

  • Basic data warehousing: tables, columns, joins, and what a SQL query does.
  • Dimensional modeling — organizing data into fact tables (events/measurements) and dimension tables (descriptive attributes). Canonical dataset = a single, governed, authoritative table for a concept.
  • Semantic layer — a place where business metrics ("active users," "revenue") are defined once in code, so any tool calling that definition returns the same number.
  • Data lineage — the dependency graph showing how raw tables are transformed into downstream models.
  • LLM agent & "Skills" — an agent is an LLM that can call tools and take multi-step actions; in Claude Code, a Skill is a folder of procedural knowledge that tells the agent how to perform a task.

1. Background & Motivation

Every company wants self-service analytics — but the common approaches each break in a specific way:

ApproachFailure
Broad data access for everyoneInconsistent metric definitions and confusion — five people compute "active users" five different ways.
Locked-down dashboards onlyMisses real business questions; metrics multiply to cover every case ("metric bloat").
LLM analytics agentRisks confident-but-wrong answers when users lack the infrastructure knowledge to validate them.

Anthropic frames the root cause precisely:

"The central problem comes down to our ability to map a user's question to specific and up-to-date entities in our data model."

They identify three failure modes that account for "an overwhelming majority of inaccurate responses." The whole architecture is organized around defeating these three:

Failure modeWhat goes wrong
Concept ↔ Entity ambiguityOne concept ("active users") maps to hundreds of plausible data options. The agent picks a wrong-but-believable one.
Data stalenessSchemas and definitions change constantly; yesterday's correct answer is today's subtle error.
Retrieval failureThe right information exists, but the agent can't find it in a vast search space.

2. Core Concepts

The four-layer stack

The architecture stacks four layers, each building on the one below. Foundations make the data trustworthy; Sources of Truth make the right answer exist; Skills make it findable; Validation makes it verifiable and catches drift.

        ┌──────────────────────────────────────────────┐
        │  4. VALIDATION                                 │
        │  offline evals · ablation · adversarial review │
        │  provenance footers · correction harvesting    │
        ├──────────────────────────────────────────────┤
        │  3. SKILLS  (procedural "how-to")              │
        │  knowledge skills (routers) + unbook skills    │
        ├──────────────────────────────────────────────┤
        │  2. SOURCES OF TRUTH  (priority order)         │
        │  semantic layer › lineage › query corpus ›     │
        │  business context                              │
        ├──────────────────────────────────────────────┤
        │  1. DATA FOUNDATIONS                           │
        │  dimensional models · canonical datasets ·     │
        │  CI enforcement · metadata as a product        │
        └──────────────────────────────────────────────┘
   targets →  ambiguity · staleness · retrieval failure

Canonical dataset

Definition: a single governed table designated as the authoritative source for a concept. Why it matters: it collapses "hundreds of plausible options" down to one, directly attacking concept-entity ambiguity. Enforced through tooling, CI checks, and mandate, with all data code colocated in unified repositories.

Semantic layer

Definition: compiled metric definitions — the highest-priority source of truth. Why it matters:

"If a question maps cleanly to a defined metric, the agent calls a function and gets one number, the same number every other surface in the company produces."

Note

Division of labor: "we recommend generating the documentation with Claude, but having a human own the definition." Claude drafts; a human is accountable for what the metric means.

Skills: two types

Skills encode how to navigate ambiguity and run analyses correctly — procedural knowledge, not facts.

Knowledge skills (thin routers)

They "allow additional domain details to load on demand" — consulting the semantic layer first, then narrowing to "~30 reference files for this domain describing the relevant tables, columns, joins and gotchas." This keeps the agent from drowning in context: load only what the question needs.

Unbook skills (analyst workflows)

They encode a senior analyst's process: "clarify the question, find sources (via the knowledge skill), run the query, and then loop the result through adversarial review sub-agents." They also bundle reusable analysis patterns like retention curves and funnel analysis.

Impact

Without skills, Claude scored 21% on analytics questions. With them, accuracy was "consistently above 95% in aggregate and regularly around 99% in certain domains."

3. Detailed Walkthrough

Layer 1 — Data Foundations

  • Dimensional modeling and standard data-engineering hygiene.
  • Canonical datasets reduce ambiguity to single governed sources.
  • Enforcement via tooling, CI checks, and mandate — not good intentions.
  • All data code colocated in unified repositories.
  • Metadata treated as a first-class product, not an afterthought.

Layer 2 — Sources of Truth (a priority decision tree)

The agent walks these in order; each step is a fallback for when the previous one can't answer.

#SourceHow it's used
1Semantic layer (mandatory first)If the question maps to a defined metric, call the function → one canonical number.
2Lineage & transformation graphWhen no metric exists, lineage turns "I don't know the metric" into "I know which governed model to aggregate from."
3Query corpusHistorical SQL — but distilled into structured reference docs and reusable patterns, because raw retrieval failed (see below).
4Business contextKnowledge graphs, roadmaps, org structure. "An agent that doesn't understand your business will answer what the user asked, but not what they meant."
Counterintuitive finding

Raw query access was largely ineffective: "Unstructured retrieval couldn't map a new question to the right precedent." The fix wasn't more data — it was structuring the precedent into reference docs.

Layer 3 — Skills

See Core Concepts for the knowledge-vs-unbook distinction. Operationally, skills consult sources in prioritized order, navigate ambiguous data, and recognize analysis patterns — turning the priority tree above into something the agent actually executes.

Layer 4 — Validation

Because "data is not software," correctness has to be measured continuously. Five mechanisms:

Offline evaluations

  • Dashboard-based evals — auto-generated by Claude, human-validated, covering common questions.
  • Long-tail evals — Claude generates plausible questions from business context, to cover the rare cases.
  • Stable ground truth: anchor to a snapshot date, write against a stable fact table, or have the grader judge the agent's query rather than its number (so a changing live number doesn't break the test).

Ablation testing

Hold the eval set fixed, vary one component, measure the delta. This is how they learned that grep access to thousands of SQL files "moved [accuracy] by less than a point in either direction."

Adversarial review

A skill that "aggressively challenge[s] all underlying assumptions on a potential final answer" — run as sub-agents. It bought +6% accuracy at the cost of +32% tokens and +72% latency.

Provenance footers

Every answer states which source tier it came from (semantic layer › curated reference › raw table), how fresh the data is, and who owns the model — so users can gauge trust at a glance.

Correction harvesting

"A scheduled agent scans stakeholder channels every few hours for similar correction language, drafts a one-line fix to the relevant reference doc, and opens a PR tagged to the domain owner."

Keeping skills from going stale

  • Skill files are colocated with the transformation models they describe.
  • Code-review hooks flag unreported model changes.
  • ~90% of data-model PRs now include skill updates — maintenance is built into the normal dev loop.

4. Worked Example

[Analysis] — a faithful illustration built from the article's described mechanics; not a verbatim transcript from the source.

Question from a PM: "How many active users did we have last month?"

  1. Knowledge skill routes the question to the "engagement" domain and loads only its ~30 reference files.
  2. Semantic layer (step 1): "active users" is a defined metric. The agent calls the function rather than guessing a definition → returns the one canonical number every dashboard uses. (If it weren't defined, it would fall back to lineage to find the governed model to aggregate.)
  3. Unbook skill applies the standard workflow: clarify ("last month" = last full calendar month), run the query, then pass the result through adversarial review sub-agents that challenge assumptions ("Did you exclude internal test accounts? Is the month boundary in the right timezone?").
  4. Provenance footer attaches: Source: semantic layer · data fresh as of 2026-05-31 · owner: @growth-data.
  5. If the PM later replies "that's too high, it includes bots," correction harvesting catches the phrase, drafts a one-line fix to the reference doc, and opens a PR to the domain owner.

The reference docs each follow a consistent template:

- Business Context
- Entity Grain
- Standard Hygiene Filters
- Dimensions & Key Tables
- Gotchas
- Best Practices / Common Patterns
- Cross-References

5. Deeper Insights

The bottleneck is mapping, not access

The single most instructive experiment: direct grep over the entire SQL corpus (thousands of files) changed accuracy by <1 point. Lesson: if your agent is wrong, throwing more raw data at it won't help — the problem is connecting the question to the right entity. Invest in structure (canonical datasets, semantic layer, distilled references), not retrieval volume.

More documentation can make things worse

Stacking extra doc refinement produced "three consecutive net-negative iterations: the docs were getting longer, not better." Lesson: there are diminishing — even negative — returns to verbosity. Concise, well-structured references beat exhaustive ones.

Validation quality depends on model quality

Swapping the adversarial reviewer for a cheaper model "lost most of the accuracy wins, for no real speedup." Lesson: the reviewer is doing real cognitive work; don't cut costs there.

Why "data is not software"

In coding, the compiler/tests are a free correctness signal. In analytics, a query runs fine and returns a number that looks plausible but is wrong. There's no inherent guardrail — which is exactly why the validation layer (provenance, evals, adversarial review) has to manufacture one.

The query corpus is raw material, not a source of truth

The historical SQL from dashboards, notebooks, and prior analyses looks like it should be the highest-value asset — it's a record of every question already answered correctly. Intuitively, point the agent at it and let it find precedents. In practice, giving the agent raw retrieval access to thousands of prior queries moved accuracy by less than a point: unstructured retrieval couldn't map a new question to the right precedent.

What does work is distilling that corpus into structured per-domain reference docs and reusable analysis patterns described in skills. The lesson: treat query history as raw material for curation, not as a source the agent reads directly. The value is real, but it has to be refined into structure before the agent can use it.

The unifying principle

"Our greatest gains have come from addressing each of the three failure modes: collapsing ambiguity into a single governed answer, making the answer easily discoverable, and flagging when either has gone stale."

6. Limitations & Open Questions

  • Presupposes mature data engineering. [Analysis] The whole stack assumes you can create canonical datasets and a semantic layer with CI enforcement. Many orgs lack this discipline, so the "start small" advice may still be a large lift for them.
  • ~95% accuracy still means ~1 in 20 answers is wrong. [Analysis] The article notes data scientists tolerate more errors than business users — but it doesn't deeply address how end users distinguish the wrong 5% beyond the provenance footer.
  • Cost/latency of high accuracy. Adversarial review's +32% tokens / +72% latency is a real tax; the piece flags the tradeoff but doesn't give a framework for where to draw the line.
  • Generalization unaddressed. [Analysis] Results are from Anthropic's own data culture and (presumably) strong models. How much transfers to a weaker model or messier org is an open question.
  • "Human owns the definition" has scaling limits. [Analysis] As metric count grows, human ownership of every definition could become its own bottleneck.
